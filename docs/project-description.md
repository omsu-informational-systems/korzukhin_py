# Проектный документ: SMA Crossover Strategy Service

## 1. Определение проекта
* **Название сервиса:** `sma-crossover-strategy`
* **Назначение:** Автоматический анализ ценовых графиков и генерация торговых рекомендаций (сигналов) для покупки и продажи активов.
* **Торговая идея:** Стратегия следования за трендом на основе пересечения быстрой (Fast SMA) и медленной (Slow SMA) простых скользящих средних. Если Fast SMA пересекает Slow SMA снизу вверх — формируется сигнал на покупку (`BUY`), сверху вниз — на продажу (`SELL`), при отсутствии пересечения — удержание (`HOLD`).
* **Решаемая проблема:** Устранение человеческого фактора (эмоциональных решений трейдера) и сокращение задержки реакции на смену рыночного тренда за счет автоматического расчета индикаторов.
* **Цели и задачи:**
  * Принимать историю рыночных свечей OHLCV через HTTP REST API и валидировать корректность данных.
  * Рассчитывать значения Fast SMA и Slow SMA по ценам закрытия свечей.
  * Формировать структурированный торговый сигнал `BUY`, `SELL` или `HOLD`.
  * Предоставлять стандартизированный эндпоинт проверки состояния `GET /health`.
* **Ожидаемый результат:** Контейнеризированный микросервис с REST API расчета сигналов и мониторинга работоспособности, готовый к интеграции с преподавательской платформой.

## 2. Границы проекта
* **Что входит в сервис:**
  * Алгоритм расчета Fast SMA и Slow SMA и определение момента их пересечения на основе переданной истории свечей.
  * Валидация входных рыночных данных (хронологический порядок свечей, корректность соотношения цен High/Low/Open/Close, наличие часового пояса).
  * REST API: `POST /signals` для генерации сигнала и `GET /health` для проверки состояния.
  * Конфигурация параметров стратегии и сервиса через переменные окружения (`SERVICE_NAME`, `APP_VERSION`, `PORT`, `SMA_FAST_PERIOD`, `SMA_SLOW_PERIOD`).
* **Что заведомо находится за его пределами:**
  * Хранение денежных средств, учет балансов, управление рисками и портфелем пользователей (зона ответственности преподавательской платформы).
  * Прямое подключение к биржевым шлюзам (FIX/WebSocket) и выставление реальных рыночных заявок.
  * Управление учетными записями трейдеров и графический пользовательский интерфейс (GUI).
  * Долговременное хранение истории котировок (сервис работает в режиме stateless и анализирует пакет свечей, переданный в запросе).
* **Контролируемые данные и решения:** Сервис полностью контролирует валидацию входного пакета свечей, математический расчет скользящих средних и выпуск аналитического сигнала (`BUY`/`SELL`/`HOLD`), но не принимает финального решения об исполнении ордера на бирже.
* **Пользователи и внешние системы:**
  * **Преподавательская платформа (Execution & Market Data Platform):** основная внешняя информационная система, которая поставляет исторические свечи и потребляет сгенерированные торговые сигналы.
  * **Оператор / Администратор:** настраивает переменные окружения, запускает контейнер и контролирует доступность сервиса.

## 3. Взаимодействие с внешними системами
Сервис взаимодействует с **Преподавательской платформой** по модели «запрос — ответ»:
* **Входные данные (`POST /signals`):** JSON-объект, содержащий тикер инструмента (`symbol`) и упорядоченный по возрастанию времени массив свечей `candles` (`timestamp`, `open`, `high`, `low`, `close`, `volume`).
* **Выходные данные:**
  * При расчете сигнала (`POST /signals`, HTTP `200`): JSON с полями `signal_id` (UUID), `symbol`, `action` (`BUY` | `SELL` | `HOLD`), `timestamp` последней свечи, `confidence` (`1.0` или `0.0`), `fast_sma`, `slow_sma`.
  * При проверке здоровья (`GET /health`, HTTP `200`): JSON со статусом `UP`, именем сервиса, версией в формате SemVer и полем `components` (в версии 1.0 зарезервировано, возвращается пустым объектом `{}`).
* **Протоколы и обоснование выбора:** Выбран синхронный протокол HTTP/1.1 REST с форматом обмена данными JSON, так как он универсален, не требует сложных клиентских библиотек на стороне платформы и обеспечивает прозрачную диагностику ошибок валидации.
* **Аутентификация:** Эндпоинт `GET /health` открыт без авторизации для беспрепятственного опроса системой мониторинга. Для `POST /signals` предполагается работа внутри изолированной доверенной сети контейнеров либо передача API-ключа/токена в заголовке `Authorization` (вынесено в открытые вопросы).
* **Ограничения и возможные ошибки:**
  * Для фиксации пересечения требуется не менее `SMA_SLOW_PERIOD + 1` свечей.
  * Временные метки должны содержать часовой пояс и строго возрастать.
  * При нарушении формата, хронологии или нехватке истории сервис возвращает HTTP `422 Unprocessable Entity` с описанием причины.
* **Допущения:**
  * Расчет SMA выполняется строго по ценам закрытия (`close`) закрытых свечей без учета незавершенных тиков.
  * Вся необходимая для расчета история свечей передается платформой в каждом запросе.
* **Открытые вопросы:**
  * Требуемый механизм аутентификации запросов от преподавательской платформы (API-ключ, JWT или mTLS).
  * Максимальная частота запросов и допустимое время ответа (SLA) при боевом тестировании.

## 4. Состав решения
1. **Серверное приложение (Strategy App на FastAPI):**
   * *Назначение и зона ответственности:* Прием HTTP-запросов, валидация входных данных через схемы Pydantic, расчет индикаторов Fast/Slow SMA, формирование сигналов и отдача статуса здоровья `/health`.
2. **Пользовательский интерфейс (Swagger UI / OpenAPI):**
   * *Назначение и зона ответственности:* Отдельный фронтенд для трейдеров не требуется по границам проекта; для ручного тестирования и просмотра контрактов API используется встроенный в FastAPI интерфейс документации (`/docs`), который автоматически доступен при запущенном контейнере и не требует отдельного развёртывания.
3. **База данных (не используется в первой версии / PostgreSQL в перспективе):**
   * *Назначение и зона ответственности:* Поскольку алгоритм SMA требует лишь короткого окна последних свечей (`SMA_SLOW_PERIOD + 1`), в текущей версии применена архитектура без сохранения состояния (stateless), что исключает накладные расходы и точки отказа БД. При появлении требования аудита сгенерированных сигналов планируется подключение PostgreSQL.
4. **Брокер сообщений (не используется в первой версии / RabbitMQ в перспективе):**
   * *Назначение и зона ответственности:* Для синхронного запроса расчета по пачке свечей достаточно прямого HTTP-вызова. При переходе платформы на потоковую рассылку котировок в реальном времени возможна интеграция через брокер сообщений RabbitMQ.

## 5. Роли и ответственность
В проекте оставлены только роли, непосредственно участвующие в жизненном цикле микросервиса:
* **Заказчик / Владелец внешней системы (Преподавательская платформа):** Формулирует требования к контрактам взаимодействия (`/health`, `/signals`), выступает поставщиком рыночных котировок и потребителем торговых сигналов. *Обоснование:* без владельца платформы невозможно согласовать формат API и критерии приемки.
* **Разработчик:** Проектирует архитектуру, реализует алгоритм стратегии SMA Crossover, пишет модульные тесты, настраивает `Dockerfile` и ведет техническую документацию. *Обоснование:* ключевая роль для создания, тестирования и поддержки кодовой базы.
* **Оператор / Администратор:** Отвечает за сборку и запуск Docker-контейнера, конфигурацию переменных окружения (`SMA_FAST_PERIOD`, `SMA_SLOW_PERIOD`, `PORT`) и мониторинг работоспособности через `GET /health`. *Обоснование:* разделение разработки кода и эксплуатации контейнера в целевом окружении.
*(Роли розничного трейдера, риск-менеджера и администратора БД исключены, так как интерфейс терминала, управление капиталом и хранение истории вынесены за границы сервиса).*

* **Средство ведения документации — Markdown в репозитории (Docs-as-Code):** Позволяет хранить проектный документ (`docs/project-description.md`) и `README.md` рядом с исходным кодом, отслеживать историю правок через Git и читать документацию прямо в браузере.
* **Язык и программный каркас — Python 3.11 + FastAPI + Pydantic v2:** Python удобен для лаконичной реализации математических и аналитических алгоритмов. FastAPI обеспечивает высокую производительность, поддержку `lifespan` для корректного завершения процесса и автоматическую генерацию OpenAPI-схем, а Pydantic гарантирует строгую валидацию входных свечей.

* **Способ локального запуска — Docker:** Изолирует приложение и его зависимости на базе легковесного образа `python:3.11-slim`, гарантируя сборку и запуск сервиса одной командой на любом компьютере без ручной настройки окружения.

## 7. Примеры запросов и тестирование

### Проверка состояния сервиса

```bash
curl http://localhost:8000/health
```

Ожидаемый ответ (HTTP 200):

```json
{
  "status": "UP",
  "service": "sma-crossover-strategy",
  "version": "1.0.0",
  "components": {}
}
```

### Генерация торгового сигнала

Эндпоинт `POST /signals` принимает символ и упорядоченный по времени массив свечей OHLCV. Для работы со стандартными периодами (Fast=10, Slow=30) необходимо передать не менее 31 свечи. При нехватке данных сервис вернёт HTTP 422 с описанием причины.

Пример запроса с curl и ожидаемый ответ — в [README.md](../README.md). Альтернативно: откройте `http://localhost:8000/docs` и воспользуйтесь встроенным Swagger UI (`POST /signals → Try it out`).

### Запуск тестов

Внутри Docker-контейнера (рекомендуется — Python 3.11 и все зависимости уже установлены):

```bash
docker run --rm sma-crossover-strategy:latest python -m unittest discover -s tests
```

Локально (требуется Python 3.11, активированное виртуальное окружение и установленные зависимости):

```bash
python -m unittest discover -s tests
```

> Локальный запуск на Python 3.14 может не сработать из-за несовместимости `pydantic-core`. Рекомендуется Python 3.11.
